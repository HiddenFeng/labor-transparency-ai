# v0.7.2 ChatGPT Sites 大众交互版设计与边界

日期：2026-09-15。阶段：`SITES_READY_LOCAL_VERIFIED` 开发/验收候选；等待用户在 ChatGPT Sites 中进行真实平台级数据库、身份、权限与调度测试。

## 目标

v0.7.2 继续采用“公开轻量互动优先、非必要基础设施不扩张”的路线，并保留 v0.7.1 的**匿名辅导/代办**闭环；本轮重点从“功能已经能跑”升级到“普通劳动者愿意看、看得懂、知道下一步怎么做”。公共体验不再以工程能力说明为首屏，而以劳动者痛点、行动入口、权益指导、真实公开案例和正式外部资源为主。

原 Python/FastAPI v0.6.1 不删除。它继续承担更完整的研究/运营能力基线；`sites-app/` 是 ChatGPT Sites 的轻量部署适配层。

## 公共体验定位

v0.7.2 的设计关键词是：**公共服务、公益媒体、支持感、温暖与力量**。首页按普通劳动者的真实决策顺序组织：

`我遇到了什么 → 我现在先做什么 → 类似事件发生过什么 → 我能找谁 → 公司/社区记录怎么看 → 我可以匿名求助什么`

首屏只突出三条普通用户主路径：匿名求助、查看公司记录、提交公开线索；运营审核入口降到页脚。系统码如 E0/E3 在普通用户界面翻译成“未核实线索 / 已核对范围与来源”等自然语言，内部证据规则不变。

新增的案例与外部资源位于 `public/editorial-content.js`。案例只用于教育性解释和行动提示，不自动进入公司事实库；外部资源只是公开导航，不代表项目与 ILO、WRC、ITUC、Workers United、政府机构或其他组织存在合作、授权、隶属或正式转介关系。

视觉系统以暖白、珊瑚红、深靛蓝和青绿为核心，使用大号编辑式标题、少量手写感短句、柔和渐变与层级化留白。动画只做轻微进入/悬停反馈，并为 `prefers-reduced-motion` 提供静态降级。

## 完整用户循环

公开证据主线：

`创建公司空间 → 社区正/负参与 → 提交公司/产品/劳动资料 → E0公开 → 证据审核 → 独立再分发复核 → 高证据/公益数据 → 纠错/撤回 → 重审`

匿名辅导主线：

`匿名去身份化提交 → 一次性高熵回执码 → 后台持久待办 → 每日 Agent 处理 → 个案私有建议 → 同会话/回执查询 → 公开聚合日报 → 可撤回`

两条主线不会互相污染：匿名辅导正文不会自动变成公司事实、劳动证据、社区热度或公开数据。

## 匿名辅导的数据边界

允许：问题类别、宽泛地区、在职/离职等工作关系状态、去身份化事件摘要、希望结果、已经尝试的步骤、紧急程度、可选的站内公司空间关联。

禁止：

- 真实姓名或私人联系方式；
- 身份证/护照等证件号码或扫描件；
- 家庭详细住址；
- 健康/医疗记录；
- 银行卡、银行账户或支付数据；
- 文件/图片/敏感附件；
- 外部机构账号密码或其他凭据。

服务端对明显邮箱、长号码和敏感字段提示做失败关闭检查。启发式过滤不是绝对匿名保证，因此 UI 同时要求用户主动去身份化。

## 匿名回执与访问

服务生成 `ADV-...` 高熵回执码，只在提交成功时返回一次。持久化状态只保存 SHA-256 回执哈希，不保存明文码。回执码等同 bearer credential：不能放入 URL、公开日志、分析埋点或日报。

同一浏览器会话通过匿名 HttpOnly cookie owner 直接读取自己的辅导记录；丢失会话后，可在 POST 请求正文中提供回执码恢复读取。Sites 若支持 Sign in with ChatGPT，应优先映射稳定用户身份，但仍保留回执恢复能力或明确迁移方案。

## Agent 每日处理

本地 runner `scripts/advisory-agent.mjs` 支持有限单次和固定时间循环。每条待办生成：

- 情况理解；
- 具体整理/行动顺序；
- 注意事项；
- 何时升级到官方劳动机构、工会、法律援助或持证专业人士；
- 固定提示：如未来需要全自动持续跟进，需另行建立专门联系渠道；当前站点不收集联系方式，也未配置自动外部联系或正式机构代提交。

建议是操作整理辅助，不是法律意见，不保证结果，也不代表任何正式机构已受理。

## 公开日报

日报只包含：日期、收到数量、当日已生成建议数量、当前待处理数量，以及满足最小样本阈值的类别统计。少于 3 条的类别合并为“其他/小样本合并”。日报不包含：个案正文、公司、回执码、owner、建议全文或任何私人标识。

## 当前自动公司资料研究：完整度结论

**流程闭环：已完成（仅针对已支持来源）。来源覆盖：未完成。**

Python back office 当前已经具备：

`公开真实公司登记 → research task → 有限网络采集 → 重试/租约/预算/缓存 → 主体消歧 → 草稿 → 独立运营复核 → 到期发布 → 请求者/关注者通知 → 持久化恢复`

当前来源矩阵：

| 栏目 | 状态 | 来源/说明 |
| --- | --- | --- |
| 法律实体身份 | `AUTOMATED_SUPPORTED` | GLEIF：法律名称、LEI、登记国家/地区、辖区、实体/维护状态 |
| 会计合并母公司 | `AUTOMATED_PARTIAL` | GLEIF 直接/最终会计合并母公司；不等于完整股权/控制关系 |
| 业务/产品 | `NO_APPROVED_AUTOMATED_SOURCE` | 尚未接入合法稳定自动来源；社区可补充 |
| 厂区/地点 | `NO_APPROVED_AUTOMATED_SOURCE` | 尚未接入 |
| 供应链/合作 | `NO_APPROVED_AUTOMATED_SOURCE` | 尚未接入；不能从 GLEIF 母公司关系推断 |
| 劳动条件 | `COMMUNITY_EVIDENCE_ONLY` | 依赖社区贡献 + 证据审核；无可靠通用自动来源 |
| 官方沟通/申诉渠道 | `NO_APPROVED_AUTOMATED_SOURCE` | 尚未接入 |

因此，不能说“系统已经自动搜集公司相关所有类型信息”。可以说：**现有 GLEIF 支持范围内，自动研究的任务、采集、审核和发布流程已经闭环；整体来源覆盖仍是部分完成。**

机器审计证据：`qa/v0_7/company-research-audit.json`。

## Sites 迁移方式

当前本地 QA 使用原子 JSON `FileStore`，用于真实验证写入、并发串行、重启恢复和访问控制；它不是 Sites 生产数据库方案。迁移时优先保留领域规则，只替换：

1. `FileStore` → Sites 实际数据库/持久化；
2. 匿名 cookie owner → Sign in with ChatGPT（若实际支持）或受支持匿名身份；
3. evidence/export/advisory 三类本地运营令牌 → Site owner/operator server-side 权限；
4. `advisory-agent.mjs` 固定时间 loop → Sites 原生 scheduler/background action；若没有，就明确保持外部/手工有限触发，不能冒充自动调度。

Sites 私有版本的正式验收不是“页面能打开”，而是要重新跑完整两条闭环、重启/版本更新持久化、并发写、用户隔离、运营权限、日报无泄露和删除/保留策略。
